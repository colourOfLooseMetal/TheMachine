# Change summary — 2026-06-11

Search-speed + load-time optimization pass over the engine and the corpus load
path. Scoring math/constants are untouched — only the plumbing around the
matcher changed. For comparing against a local checkout: three files were
modified (`wams.cpp`, `js/app.js`, `CLAUDE.md`) plus this summary.

## wams.cpp — the engine

### Stage 1 (fuzzy bitap filter)
- **Before:** `SearchStringFuzzy(std::string text, std::string pattern, int k)`
  was called per line. Every call copied the caption AND the pattern into fresh
  `std::string`s (heap allocs), heap-allocated the `R` array with `new[]`, and
  rebuilt the 128-entry `patternMask` + pattern-bit loop — ~365k times per search.
- **After:** signature is `SearchStringFuzzy(const char* text, const unsigned
  long* patternMask, unsigned long* R, int m, int k)`. All query-only prep
  (mask table, `R` buffer, the `m > 31` cap and empty-query early-outs) happens
  once per search in `cppSearch`. Lines shorter than `queryLen − k` are skipped
  before scanning, using the new O(1) `lineLen(i)` (offset gap, no strlen).
- **Bugs fixed in the same code:**
  - `new unsigned long[(k + 1) * sizeof *R]` allocated 8× too much **and** was
    released with `free()` on `new[]` memory (undefined behaviour).
  - `patternMask[text[i]]` indexed with *signed* char → negative-index UB on
    any non-ASCII byte. The mask is now a 256-entry table indexed as
    `unsigned char`.

### Work arrays → survivor list
- **Before:** four full-corpus arrays (`scoresArr`, `sortedIndices`, `g_bitSet`,
  `g_matchIndex`) sized to `g_totalLines`, all `std::fill`ed at the start of
  every search (~5 MB of memsets) and two of them filled again at the end of
  `search()`. `ensureWorkArrays` managed their sizing.
- **After:** one `std::vector<Survivor> g_survivors` with
  `{int line; short matchIdx; double score;}`. Stage 1 pushes hits, stage 2
  fills scores, stage 3 sorts it. All the per-search fills are gone.

### Stage 3 (sort)
- **Before:** `hashSortIndices` — counting sort over ALL lines' scores via two
  `std::map<double, int>`s (tree node allocations, O(log) lookups per element).
- **After:** `std::partial_sort` of just the survivors for the top 450,
  comparator = score desc, line index asc — the same tie ordering the counting
  sort produced. `hashSortIndices` deleted.

### Stage 2 (jaro sliding window)
- **Before:** `jaro_sliding_window` took the line and pattern as `std::string`
  by value; every slide step allocated a `string.substr(...)` window AND a
  `" " + s2 + " "` padded pattern.
- **After:** new `PaddedQuery` struct (`q`, `" "+q`, `q+" "`, `" "+q+" "`)
  built once per search in `cppSearch`; window slices are pointer offsets into
  the corpus (`lineAt(i) + e - 1`), no copies. `jaro_actual_search` /
  `jaro_actual_search_but_with_window_bs` now take `const char*` — the match
  loops inside are character-identical to before.

### Result packing / return
- **Before:** `escape_json` built each caption through an `ostringstream`;
  `Scores::to_json` returned `new char[json.length()]()` + `strcpy` — a 1-byte
  heap overflow (the `'\0'` lands past the end) cleaned up with the wrong
  `delete` form.
- **After:** `escape_json` appends into a plain string; `Scores::to_json`
  returns one `std::string` and `search()` hands `json.c_str()` straight to
  `EM_ASM`. No copy, no overflow.
- **Behavior change (intentional):** when fewer than 450 lines pass the bitap
  filter, the payload is no longer padded out to 450 with zero-score junk
  lines — only real survivors come back, so the "N results" count is accurate.

### Native build support
- emscripten-specific bits (`#include <emscripten.h>`, the `EM_ASM` callback)
  are behind `#ifdef __EMSCRIPTEN__`, and `main()` is now a working native test
  driver: `g++ -O3 wams.cpp -o wams && ./wams "query" data/sm.txt ...` loads
  the .txt files through the same exports JS uses and prints the top 450 as
  `index<TAB>score<TAB>caption` (timing on stderr).

## js/app.js — corpus load path

- **Parallel show downloads:** `loadSelection` used to `await fetch(...)` one
  show at a time (12 serialized round trips, ~12 MB). New `fetchShows()` starts
  all fetches at once via `Promise.all`; the `showWritePtr`/`commitShow` commit
  loop still runs in manifest order, so `loadedShows[]` / index mapping are
  unchanged.
- **Downloads overlap the wasm compile:** `fetch('manifest.json')` (and on
  desktop a whole-corpus prefetch, `g_eagerBuffersPromise`) now start at script
  parse time instead of inside `Module.onRuntimeInitialized`. Only the
  commit-into-wasm step waits for the runtime. The eager prefetch is handed to
  the initial `loadSelection` only when the initial selection is still
  all-shows, and is dropped after startup (one-shot).
- `isMobile` detection hoisted to parse time as `g_isMobile` (same regex).

## CLAUDE.md

Updated to match: pipeline steps 4–7, the engine function roster
(`Survivor`/`g_survivors`, `lineLen`, `PaddedQuery`, new `SearchStringFuzzy`
signature, removal of `ensureWorkArrays`/`hashSortIndices`), the front-end

## Verification performed

- Built the previous (HEAD) engine and the new one natively with g++ -O3 and
  compared full-corpus (all 12 shows, 365,697 lines) results for 18 query
  shapes: common words, 1–2 char queries, phrases, apostrophes/quotes, double
  spaces, no-match strings, a 30-char query, and a >31-char query.
  **Every positive-score result (text, index, exact double score) was
  identical**; the only difference is the removed zero-score padding tail.
- Native timing on the same hardware: ~2× faster across queries (e.g. "hello"
  167 ms → 72 ms, "hi" 279 ms → 112 ms; the >31-char no-op case 30 ms → 0.01 ms).
  Wasm should see at least this much, since stage 1's per-line allocations were
  the dominant cost.
- Repeated-search + `clearCorpus`/reload state-reuse test: identical results
  across back-to-back searches and after a corpus rebuild.
- `node --check` on `js/app.js`; the `__EMSCRIPTEN__` branch syntax-checked.
  The actual wasm build still needs a local `.\build.ps1 -Debug -Serve` run.
