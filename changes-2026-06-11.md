# Change summary — 2026-06-11

Search-speed + load-time optimization pass. Three files were modified
(`wams.cpp`, `js/app.js`, `CLAUDE.md`) plus this summary. The actual matching
and scoring math is **unchanged** — verified by comparing old vs new engine
output on the full corpus (details at the bottom). Native search time roughly
halved; page load now downloads everything in parallel.

## The changes in plain terms

### 1. Stop re-doing query setup for every line (wams.cpp, stage 1)

**What was happening:** before scanning each caption line, the bitap filter
rebuilt a lookup table for the query, allocated a scratch buffer, and made
heap copies of both the line and the query. None of that depends on the line —
only on the query — yet it ran ~365,000 times per search (once per line).

**The fix:** do all the query setup once at the start of the search, then scan
every line with just the cheap inner loop. Also skip lines that are too short
to possibly contain a match, without scanning them at all.

**Why it matters:** this setup work was the single biggest cost of a search —
bigger than the actual matching.

### 2. Only sort the matches, not the whole corpus (wams.cpp, stage 3)

**What was happening:** after scoring, the engine sorted the scores of ALL
365k lines (using two tree-based maps) just to find the top 450, and wiped
~5 MB of scratch arrays clean before every search.

**The fix:** lines that pass the filter go into a small "survivors" list
(usually hundreds, not hundreds of thousands), and only that list gets
partially sorted for the top 450. The big scratch arrays are gone entirely.

**Why it matters:** sorting 365k entries to keep 450 was almost all wasted
work; so were the 5 MB of array wipes per search.

### 3. Stop allocating strings while the window slides (wams.cpp, stage 2)

**What was happening:** for every position the query slides across a matching
line, the code cut out a fresh substring of the line and built a fresh
space-padded copy of the query ("` hello `") — two heap allocations per step,
for every survivor.

**The fix:** the padded versions of the query are built once per search, and
the "window" into the line is just a pointer offset into memory that already
exists. Zero copies. The scoring code that reads the characters is unchanged.

### 4. Fix some hidden memory bugs found along the way (wams.cpp)

These were all in the code being restructured anyway:

- A scratch buffer was allocated 8× larger than needed, and freed with the
  wrong function (`free()` on `new[]` memory — technically undefined behavior).
- Lines containing non-ASCII bytes could index *before* the start of the
  lookup table (also undefined behavior). The table is now 256 entries and
  indexed safely.
- The JSON result string was copied into a buffer exactly one byte too small
  (the terminating `'\0'` landed past the end — a real heap overflow), then
  freed with the wrong `delete` form. The result is now a normal `std::string`
  handed straight to the JS callback, no copy at all.

### 5. More honest result counts (small intentional behavior change)

Previously, if fewer than 450 lines matched, the engine padded the results out
to 450 with random zero-score lines, so you'd see junk at the bottom and the
"N results" count was always 450. Now only real matches come back, so the
count is accurate and there's no junk tail.

### 6. Download all shows at once, and earlier (js/app.js)

**What was happening:** the 12 caption files (~12 MB) downloaded one at a
time — show #2 didn't start until show #1 finished. And nothing started
downloading until the wasm engine had finished downloading and compiling.

**The fix:** all selected shows now download in parallel, and the downloads
(manifest + on desktop the whole corpus) start the moment the page's script
runs, so they overlap with the wasm compile instead of waiting behind it. Only
the final "copy bytes into wasm memory" step waits for the engine to be ready.
The order shows are committed into the corpus is unchanged, so the
index→image mapping works exactly as before.

### 7. Native test build (wams.cpp)

The emscripten-only bits are now behind `#ifdef __EMSCRIPTEN__`, so the engine
also compiles as a normal command-line program for testing without the wasm
toolchain:

```
g++ -O3 wams.cpp -o wams
./wams "hello" data/sm.txt data/recess.txt     # prints top 450: index, score, caption
```

### 8. CLAUDE.md updated to match

Pipeline description, function roster, and known-rough-edges list now describe
the new structure (`g_survivors`, `lineLen`, `PaddedQuery`, the new
`SearchStringFuzzy` signature; `ensureWorkArrays`/`hashSortIndices` removed).

## Reference: renamed/removed internals (for diffing against a local copy)

| Old | New |
| --- | --- |
| `scoresArr`, `sortedIndices`, `g_bitSet`, `g_matchIndex`, `ensureWorkArrays` | `std::vector<Survivor> g_survivors` (`{line, matchIdx, score}`) |
| `hashSortIndices` (counting sort over all lines) | `std::partial_sort` of survivors, top 450, same tie ordering |
| `SearchStringFuzzy(std::string, std::string, int k)` | `SearchStringFuzzy(const char*, const unsigned long* mask, unsigned long* R, int m, int k)` — prep lives in `cppSearch` |
| `jaro_*` taking `std::string` by value, `substr` windows | `jaro_*` taking `const char*`, `PaddedQuery` built once, pointer-offset windows |
| `Scores::to_json()` → `new char[]` + `strcpy` | `Scores::to_json()` → `std::string`, `c_str()` to `EM_ASM` |
| `loadSelection(selectedShows)` — sequential `await fetch` | `loadSelection(selectedShows, prefetched?)` + `fetchShows()` (`Promise.all`) |
| manifest fetched inside `onRuntimeInitialized` | `g_manifestPromise` + `g_eagerBuffersPromise` start at parse time |

## Verification performed

- Built the previous (HEAD) engine and the new one natively with g++ -O3 and
  compared full-corpus (all 12 shows, 365,697 lines) results for 18 query
  shapes: common words, 1–2 char queries, phrases, apostrophes/quotes, double
  spaces, no-match strings, a 30-char query, and a >31-char query.
  **Every positive-score result (text, index, exact double score) was
  identical**; the only difference is the removed zero-score padding tail.
- Native timing: ~2× faster across queries (e.g. "hello" 167 ms → 72 ms,
  "hi" 279 ms → 112 ms; the >31-char no-op case 30 ms → 0.01 ms). Wasm should
  benefit at least as much, since stage 1's per-line allocations dominated.
- Repeated-search + `clearCorpus`/reload state-reuse test: identical results
  across back-to-back searches and after a corpus rebuild.
- `node --check` on `js/app.js`; the `__EMSCRIPTEN__` branch syntax-checked.
  The actual wasm build still needs a local `.\build.ps1 -Debug -Serve` run.
